# Module parity review (read-only)

Paths: A = src/modules/mc_indi_rate_control, B = src/modules/mc_indi_pos_control, stock = src/modules/mc_rate_control.

## Task 1: A vs stock MulticopterRateControl::Run()
Run() is a near copy (dt clamp, param update, ACRO path, rates_setpoint copy, NaN guards, torque NaN->0, energy status). Differences:

1. rate_ctrl_status not published (stock :238-242, A none; A has indi_rate_status instead). Only consumer in tree is the logger (logged_topics.cpp). Matters: no. Flight Review/tools lose the rate-loop plots. Autotune (rc.mc_apps:32) is still started and would tune PID params that INDI ignores -> should fix: do not start mc_autotune_attitude_control when MC_INDI_EN=1, or document.
2. Battery scaling absent (stock :253-269; A comment :311). Matters: only if MC_BAT_SCALE_EN=1, thrust then is not compensated for sag; the hover estimator partly covers it. Note.
3. Control-allocator saturation: stock uses setSaturationStatus for anti-windup; A uses unallocated_torque only as actuator model correction (:303-309, :181-185). Different but intentional. Note. Feedback is only consumed if its timestamp is newer than the last setpoint; stale/never-arriving control_allocator_status silently falls back to the model.
4. landed/maybe_landed: both read the same way (:248-255) and pass `maybe_landed||landed` to the law. Stock also resets gain compression on landed; A has no equivalent but INDI resets yaw filters while landed (indi_rate_control.cpp:342). Takeoff: no ground-contact or takeoff handling in either rate controller. No difference that matters.
5. flag_control_rates_enabled false->true: neither module resets state on this edge (stock resets integral only when disarmed, A resets only when !armed or not rotary wing, :297-301). A keeps stale `_prev_torque_setpoint`, filter states and `_rates_setpoint`/`_thrust_setpoint` across the gap. Stale measured torque is rejected by timestamp, so the main risk is stale INDI filter state and old setpoints being applied at re-entry. Should fix (suspected small): reset INDI on the rising edge of flag_control_rates_enabled.
6. Termination/kill: stock rate controller has none either (handled downstream by commander/actuators). Equal.
7. Manual ACRO path identical (:262-285). One caveat shared with stock: `_manual_control_setpoint_sub.update` gating means a lost stick topic keeps the last sticks. Equal.
8. VTOL: stock takes `vtol` arg and publishes *_virtual_mc topics (stock :48-52). A ignores args (task_spawn :369-371), always publishes plain vehicle_torque/thrust_setpoint, and rc.vtol_apps:17 only starts `mc_rate_control start vtol`. A must not be used on VTOL. Matters only for VTOL. Note; add a refusal when argv has "vtol" or vehicle is VTOL.
9. dt: identical (clamp 0.125 ms..20 ms, from timestamp_sample, first sample gets 20 ms). Equal.
10. Setpoint loss: both keep the last `_rates_setpoint`/`_thrust_setpoint` forever when vehicle_rates_setpoint stops (stock :184, A :287). With B publishing rates, a crashed/stopped B or mode change race leaves the last thrust applied indefinitely. Should fix for A+B flight: add a setpoint-age timeout (e.g. >200 ms -> zero rates, hover/last thrust, or flag fault) in A, or rely on commander (nothing does today).
11. perf counters: only `_loop_perf` in both, same. Equal. A lacks nothing there.
12. Start/stop safety: separate Descriptors (stock :46, A cpp:44); rc.mc_apps chooses one by MC_INDI_EN, but a manual `mc_indi_rate_control start` while `mc_rate_control` runs is accepted: both subscribe to vehicle_angular_velocity and both publish vehicle_torque_setpoint/thrust_setpoint/actuator_controls_status_0 on the same WQ -> torque setpoint alternates between PID and INDI. Blocker for bench safety (suspected, not run). Fix: in init() refuse if the other module is running (e.g. check `vehicle_torque_setpoint` publishers via orb_group_count or a shared lock) or one shared "rate controller" flag. Also changing MC_INDI_EN needs reboot (not noted anywhere).

## Task 2: eRPM path (DShot.cpp -> McIndiRateControl::updateMeasuredTorque -> IndiMeasuredTorque)

Driver facts (src/drivers/dshot/DShot.cpp):
- esc_status published from Run() whenever `serial_updated || bdshot_updated` (:97-107). Run is driven by the mixer (actuator_motors callback). process_bdshot_telemetry returns true only after ALL bdshot channels are ready (:650-656), so rate = output cycle rate (roughly the control allocator rate) provided every ESC answers each frame.
- esc.timestamp = hrt now of the driver Run (:678), NOT the capture time of the frame. Same for all motors. It is refreshed on every publish, even if no new eRPM frame arrived. Typical eRPM ages (DShot frame + GCR reply + ESC period averaging) are invisible to the module; MC_INDI_ERPM_DLY must model it.
- esc_errorcount = serial errors + `up_bdshot_num_errors` = read_fail_crc (cumulative CRC failures only) (:785-786; stm32 dshot.c:986-993). On a CRC failure the stm32 code sets ready (dshot.c:690) and the old erpm stays `ready` forever (never cleared on read, dshot.c:1008-1015), so the driver republishes the previous rpm with a fresh timestamp. The module's counter-change drop test (IndiMeasuredTorque.cpp:109-114) is therefore REQUIRED and is correct for stm32. Suspected gap: channels without capture DMA are marked permanently ready (dshot.c:372-375) and never raise errors -> frozen rpm with fresh timestamp, undetectable. Also EDT frames (temperature etc.) replace eRPM frames some cycles: stale rpm with fresh timestamp, no error. Should fix: add a "rpm unchanged for N cycles while armed" check or a driver-side per-motor `last_new_frame` timestamp; at least refuse to arm with a PX4_WARN capture-unsupported channel.
- esc_online_flags bit = motor_index (:770-781); online needs bdshot online (>BDSHOT_OFFLINE_COUNT consecutive CRC failures turns it off, so offline detection is slow, many frames).
- actuator_function only written in mixerChanged (:1048) per motor_index; index in esc[] = motor_index. Module loops j < esc_count and uses j both as index and flag bit, motor from actuator_function (cpp:146-159). Correct only if motor indices are contiguous from 0 (esc_count = popcount). Note (true for a plain quad).
- Pole count: param per motor, default 14; esc_rpm = erpm / (pole_count/2) with integer division, min 2 (:792, :803, :1026). MC_INDI_W_MAX must be calibrated from the same esc_rpm or the pole count is a silent gain error. Odd pole counts truncate. Note.
- esc_rpm is int32 "negative for reverse" per msg, but the BDShot path never produces a negative value (eRPM unsigned in telemetry). Reversible/3D: driver 3D scaling exists (:480-484); module uses rpm^2 so rotation direction/thrust sign is lost; also `omega >= 0` check (IndiMeasuredTorque.cpp:120). Only matters for 3D outputs. Note.
- Zero rpm/stopped motor: ESC sends erpm 0 -> u=0 valid, torque from trim; OK. While disarmed the ESC may report 0 and offline flags; module resets INDI when disarmed anyway.

Module assumptions:
- Freshness: sample age < SAMPLE_MAX_AGE_US=20 ms hard-coded (IndiMeasuredTorque.hpp:74) is measured against the driver timestamp, plus MC_INDI_ERPM_TO against the OLDEST sample (cpp:190-191). Publish period of 2.5-5 ms vs 20 ms is fine, but one slow cycle (e.g. a missed BDShot reply on one motor) invalidates the whole 4-motor torque (valid=false if any motor not fresh, :156). That is safe but the blend/fallback transition in the law (indi_rate_control.cpp:322) is the behaviour to test on hardware. Should fix: MC_INDI_ERPM_TO and the hard-coded 20 ms are two separate knobs; keep one.
- The module only drains esc_status inside the rates-enabled branch, after publishing the torque (cpp:338): the sample used at cycle n was published during cycle n-1 or earlier; accounted for by "measurement delay samples" but not measured.
- Unset esc[] entries (actuator_function 0) are skipped (motor<0). Good.

## Task 3: module B (McIndiPosControl)

1. `_landed` branch (cpp:467-481): `landed || maybe_landed` (:294). On a false maybe_landed in flight (aggressive descent at low thrust, free-fall, thrust at MPC_THR_MIN), B publishes ZERO rates and MPC_THR_MIN and resets the law; zero rates freezes attitude (does not level), thrust drops to minimum, which reinforces the detector. No recovery path other than the land detector clearing. Blocker. Fix: in flight, use only `landed` (not maybe_landed) or require ground-contact + low altitude/velocity; when "landed" trips while airborne, level + last/hover thrust rather than min.
2. Takeoff impossible from the ground in this mode (suspected, not traced end-to-end): while landed the module forces thr_min (:476) and never ramps, while the land detector needs thrust above its threshold to clear landed. Stock mc_pos_control has a takeoff ramp. Blocker for takeoff in this mode; document "take off with Takeoff/Position then switch" or add takeoff ramp when armed && landed && trajectory asks for climb.
3. Landing: no landing handling (no ground-contact slowdown, no thrust cut). On touchdown `_landed` -> thr_min + zero rates; the vehicle can tip with a tilt commanded. Should fix.
4. Failure signalling: hold() (:384-434) publishes last rates/thrust for 3 cycles then level attitude with last thrust forever and a single PX4_ERR (:419). Only indi_pos_status.failure is set. Commander gets nothing from this: arming_reply.can_arm_and_run is hard-coded true (:198). Compare mc_raptor.cpp:638-765 which sets can_arm=false on stale angular velocity/local position/attitude so commander's failsafe leaves the mode. Blocker: drive can_arm_and_run (and mode_req_*) from the same inputs_ok/hold failure state. Note: commander does enforce mode_req_angular_velocity/local_position/attitude/local_alt itself (replied :199-202), so loss of EKF validity is covered, but trajectory_setpoint staleness, ESC loss, NaN law failure and hold overflow are not. The reply is published only on request (:191), fine.
5. Arming-check reply content (:192-203): no health_component, no events, never refuses. Should fix: refuse when MC_INDI_W_MAX invalid (`_rotor_w_max<=0` silently disables telemetry thrust, :305), when no rotor telemetry, when parameters invalid.
6. Setpoint type registered = Rates only on the active edge (:210-216); the `setpoint_config_reply` is never read. Until commander applies it, ModeManagement default type is Trajectory (ModeManagement.hpp:89), so for the first cycles after activation the stock position+attitude chain is enabled and also publishes vehicle_rates_setpoint while B publishes too (race at mode entry and, since type resets to default when the mode is left, at every re-entry). Should fix: read the reply, re-send until success, and publish nothing until confirmed. Also re-publish config on module restart/mode re-register.
7. trajectory_setpoint: B ignores everything but trajectory_setpoint (cpp:284-289, 540-555). Velocity-only works (NaN position -> zero p term, indi_accel_control.cpp:223-226). All-NaN pos+vel+acc = zero velocity brake (OK). The OFFBOARD replacement means offboard attitude, rates, thrust/torque, actuator setpoints are silently ignored: a node sending them only sees the vehicle hold level at last thrust after 100 ms (kStaleTimeout) with no error. Should fix: reject in arming check/log a warning when offboard_control_mode requests attitude/body_rate/actuator.
8. EKF resets ignored: no use of xy/z/vxy/vz/heading_reset_counter anywhere in B (suspected: grep found no reset_counter or heading usage). A position reset makes p_ref-p jump (clamped by vel limits, but a step in a_c), a heading reset rotates `yaw_ref` vs attitude; stock mc_pos_control compensates setpoints on resets. INDI filters (`_lpf_f`, jerk difference) not reset. Should fix: on any reset counter change, shift p_ref/yaw_ref by delta_* or call `_indi.reset`.
9. Stale EKF: handled by freshness/validity flags with a 100 ms timeout (:497-502) -> hold. 100 ms is generous with local position at 50 Hz? ok. Note. v_xy_valid=false in flight forces level+last thrust forever (no descent/land), only commander failsafe can end it.
10. Yaw: `yaw_ref` NaN -> current yaw (indi_accel_control.cpp:325), yawspeed NaN -> 0. Matches stock behaviour (hold current heading). In hold() leveling uses current yaw. Fine. Note: offboard yaw jumps are limited only by attitude controller's rate limits (MC_YAWRATE_MAX), same as stock.
11. Thrust when rotor telemetry is lost: law falls back to `_thrust_prev*_k_cmd` model (indi_accel_control.cpp:265) after kEscMaxAge=50 ms, silent except indi_pos_status.mean_u_valid. No hover-thrust estimator feedback either; thrust model parameters (G_T, K_CMD) must be right or the first flight sags. Should fix: warn/failsafe via arming check if telemetry absent for >1 s while armed; compare mc_nn_control which checks validity in nn_control_checks.hpp.
12. Start/stop: only registers with commander at init(); if commander restarts the registration is lost (suspected). On module exit mid-flight, unregister is sent but the last rates_setpoint stays latched in A forever (see Task 1 item 10). Should fix with A-side timeout.
13. Differences vs mc_raptor/mc_nn_control: both of those publish direct actuators/their own setpoint type and gate can_arm on input health (raptor :638-765); B does not. Neither checks landed in the same way (grep of mc_raptor/mc_nn_control found no landed handling); B's landed zero-rates is its own invention and the most dangerous part.
14. dt (:510-522) from local_position timestamps, clamp 2-50 ms; first-run fallback `1/_filter_rate_hz`. measureRate needs 50 samples before the filter is configured (:156-167); `_filter_ready` false -> `_indi.setFilter` never called until then: the law runs at 20 ms default dt with an unconfigured filter during the first 50 position samples after boot if the mode is activated early. Suspected, should fix: block can_arm until `_filter_ready`.
