## (b) Missing requirements

- Rnew-1 BLOCKING: The takeoff state machine must also run while PC is disabled, with skip_takeoff=true and want_takeoff=false. Armed therefore forces state FLIGHT (TO:102-104), so Manual/Stabilized to Altitude/Position in air does not re-enter spoolup/ramp or idle thrust. On the ground, landed then drops FLIGHT to ready_for_takeoff on the first PC-on cycle (TO:91-95). R13 and R32 do not state this. (MPC:645-650; TO:102-104)
- Rnew-2 BLOCKING: SYS_VEHICLE_RESP, MPC_XY_VEL_ALL and MPC_Z_VEL_ALL are applied by mc_pos_control as writes to params owned by other consumers: MPC_ACC_HOR, MPC_ACC_HOR_MAX, MPC_MAN_Y_MAX, MPC_MAN_Y_TAU, MPC_TILTMAX_AIR (seen) and further ones declared at MPCh:186-197. If the replacement does not perform this remap, the knobs silently stop working for the flight tasks. R30 treats them as the module's own params. Whether the FMM tasks read these params was not grepped. (MPC:118-134, 166-168; MPCh:186-197)
- Rnew-3 MINOR: mc_pos_control also enforces cross-module parameter sanity and commits to storage: tilt air <= 89 and land <= air, MPC_XY_CRUISE <= MPC_XY_VEL_MAX, MPC_VEL_MANUAL/BACK/SIDE, MPC_Z_V_AUTO_UP/DN <= MAX_UP/DN, MPC_THR_HOVER within [MIN, MAX]. MPC_TKO_SPEED and MPC_LAND_SPEED are clamped locally only (no commit). Without this, tasks see unvalidated limits. (MPC:170-290, 296-297)
- Rnew-4 BLOCKING: Takeoff can start only from want_takeoff in vehicle_constraints (ready_for_takeoff to rampup, TO:72-75). Producers are FlightTaskAuto (FlightTaskAuto.cpp:236, 276: unsmoothed vz < -0.3), ManualAltitude (:316), ManualAcceleration (:93), AutoFollowTarget (:480), and OFFBOARD derived in MPC:470-492. The default is false (FlightTask.cpp:224). R11 covers only offboard; the replacement must keep reading constraints.want_takeoff as the sole trigger. Before rampup the output is idle for every mode (MPC:505, 522-526).
- Rnew-5 BLOCKING: Outputs and takeoff_status are produced only inside `if (_local_pos_sub.update(...))` (MPC:389-662) and there is no else. If vehicle_local_position stops, the 100 ms backup wake (MPC:382) publishes nothing: no attitude setpoint, no vehicle_local_position_setpoint, no takeoff_status. ATT then holds the last thrust_body/q_d (ATT:327-344 has no staleness check in the lines read). A replacement needs an explicit decision on a stale local position, since the existing module offers no protection beyond Commander. (ATT staleness handling elsewhere unverified.)
- Rnew-6 MINOR: The failsafe setpoint is LATCHED. After the enable edge with no trajectory_setpoint, MPC:451-455 stores a failsafe setpoint stamped with timestamp_sample. From the next cycle `_setpoint.timestamp >= _time_position_control_enabled`, so that frozen setpoint is reused until a real trajectory_setpoint arrives. It is not regenerated each cycle. (MPC:451-459)
- Rnew-7 MINOR: In OFFBOARD, constraints.want_takeoff and speed limits are overwritten every cycle after the speed_up clamp. speed_down NaN falls back to MPC_Z_VEL_MAX_DN (MPC:537-538). On the failsafe path constraints are reset to `{0, NAN, NAN, false}` (MPC:622). (R6 and B6 mention only part.)
- Rnew-8 MINOR: LD derives in_ground_effect from takeoff_state (RAMPUP always; FLIGHT if below LNDMC_ALT_GND_EFFECT height; also in_descend and no horizontal movement). takeoff_status must therefore stay in RAMPUP for the whole ramp. (LD:329-334, 116-120)
- Rnew-9 MINOR: takeoff_status.tilt_limit is consumed by StickAccelerationXY to cap Position-mode stick acceleration at tan(tilt_limit)*g (StickAccelerationXY.cpp:193-200). It must be published, and slewed at 0.2 rad/s from MPC_TILTMAX_LND to AIR. R5/R26 list the field but not this consumer; the default when no message exists was not checked.
- Rnew-10 MINOR: LD and HTE depend on parameters and signals the outer loop's thrust scale must match. LD uses MPC_THR_HOVER and MPC_THR_MIN (via `_params`) and hover_thrust_estimate directly in its low-throttle thresholds (LD:105-114, 222-234, 287-288). HTE starts from MPC_THR_HOVER, bounds the estimate by +/-HTE_THR_RANGE (HTE:72, 90-91), only runs when armed and `_in_air` (dist_bottom > 1 m, HTE:128-132, 158), and needs vehicle_thrust_setpoint and vehicle_attitude fresh within 20 ms plus control_allocator_status (HTE:165-172). It fuses -local_pos.az against allocated thrust (HTE:190). Extends R24.
- Rnew-11 MINOR: The hover-thrust estimate is pushed into the controller on every valid message (MPC:423-431), but MPC_THR_HOVER overwrites it each cycle until state is FLIGHT (MPC:513-515). The estimate therefore takes effect only once flying. The z integrator is shifted on each update so thrust stays continuous (PC:75-92). R25 states the end result, not this ordering.
- Rnew-12 MINOR: z and vz validity are independent (MPC:320, 348; EKF2.cpp:1731 TODO says modules do not always handle v_z_valid != z_valid). The z_deriv blend requires both z_valid and v_z_valid (MPC:582-584). R21/R31 do not state the independence.
- Rnew-13 MINOR: GotoControl detail beyond R7. The goto setpoint times out after 500 ms and is cleared when disabled (GotoControl.cpp:51-65). It runs only when no new trajectory_setpoint arrived this cycle (MPC:437-438). Its smoother is reset on invalid position (GotoControl.cpp:79-89) and on EKF resets (MPC:754-778).
- Rnew-14 MINOR: vehicle_local_position_setpoint consumers beyond R4: mavlink POSITION_TARGET_LOCAL_NED and POSITION_TARGET_GLOBAL_INT streams, so GCS shows setpoints (streams/*.hpp:58, :62). FlightTask applies a timeout (`_timeout`) and sets the feedback to NaN when stale (FlightTask.cpp:193-201).
- Rnew-15 MINOR: Build and start integration: voxl2 start scripts also start mc_pos_control (see (a)-11), and the VTOL script starts it with `vtol` (rc.vtol_apps:20). A replacement must be wired into each, plus board px4board and linker lists (not grepped).

## (c) Wrong or imprecise facts in existing items

- R9 and mode table row "Altitude (ALTCTL)" WRONG: an axis with all of pos/vel/acc NaN makes the whole setpoint INVALID (PC:231-234, "every axis x, y, z needs to have some setpoint"). Altitude and Descend modes work because xy carries an ACCELERATION setpoint (Descend: FlightTaskDescend.cpp:64, 72). xy pos/vel NaN with finite acc is the "uncontrolled" case and only resets the xy integrator (MPC:594-599). A candidate must not assume xy can be omitted entirely. ManualAltitude's xy output (:316 region) was not read; the inference follows from PC:231-234.
- Section 2 and R5, "takeoff_state (0..5 enum)": published values are 1..5 (disarmed=1, spoolup=2, ready=3, rampup=4, flight=5). 0 is UNINITIALIZED and is never produced by TakeoffState (msg/TakeoffStatus.msg:5-10; Takeoff.hpp:48-54). Consumers compare `< RAMPUP` (=4) (FMM:357).
- B12 imprecise: when vz state is also invalid, `velocity[2] = NAN` and `acceleration[2] = 0.3` replace the blind-land vz = MPC_LAND_SPEED set earlier (MPC:699-709). Blind land only survives when vz is finite. B12 also does not say the xy test uses states.velocity (filtered, NaN if invalid).
- B13/R20 imprecise: "no output until a setpoint with timestamp >= enable time" holds only for the first cycle(s) (see Rnew-6). The failsafe setpoint's timestamp is timestamp_sample (MPC:454, 667-679), so output starts the next cycle.
- R19 "never output NaN to vehicle_attitude_setpoint" is a design property, not a guard: the result of the last `_control.update` is not checked (MPC:627). Safety comes from the failsafe setpoint being finite by construction.
- B16 "MAX_SAFE_TILT_DEG value UNVERIFIED": it is 89 (MPCh:228), as R26 already states. Internal inconsistency only.
- B2/R32: PC-off branch calls updateTakeoffState(armed, landed, false, 10.f, true, ...) and resetIntegral (MPC:645-650). Correct as written, but the arguments (skip=true, vz limit 10) were not carried into R13 (see Rnew-1).
- Items spot-checked and CORRECT: B1 dt clamp (MPC:390-391), B4/B10/B14 line cites (TO:48-110; MPC:305-370; MPC:718-780), B7 idle result (PC:63-68, 217-225), B15 thrust mapping (PC:219-221, MPC:277-292), B17 collective thrust (PC:223), B18 limits and decaying ramp (MPC:550-577), B6 clamp (MPC:464-468).
